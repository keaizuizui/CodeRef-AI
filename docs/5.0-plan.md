# CodeRef-AI 5.0 开发计划（Phase 0 起步）

> 版本：v0.2（执行稿）
> 日期：2026-08-24
> 基于：《CodeRef-AI 5.0 项目规划（讨论稿）》（v0.1）
> 状态：Phase 0 骨架搭建中

---

## 一、5.0 总览

### 1.1 一句话定位

**让已经渐进到难以精准实用的项目，被人工定义的正轨推回去。**

### 1.2 与 4.X 的定位差异

| | 4.X | 5.0 |
|---|---|---|
| 定位 | 确定性现状诊断器 | 架构推回正轨的工作台 |
| 核心动作 | 扫描 → 诊断 → 报告 | 人工定义正轨 → AI 执行重构 → 验证对齐 |
| 目标架构 | 无（只和自己比健康度） | 有（人工定义，作为重构参照系） |

### 1.3 核心设计原则（继承讨论稿）

- **目标架构由人定义，不由 AI 推断**——AI 可以建议，最终确认权在人。
- **不做自动重构**——CodeRef 生成重构任务卡，执行交给编程 AI；CodeRef 负责验证。
- **确定性优先**——差距分析、影响范围、验证标准全部来自静态图谱，不依赖 LLM 猜测。
- **小步迭代**——每张任务卡只动 1-3 个模块，每步重构后立即验证。

## 三、Phase 0 详细设计

### 3.1 目标架构 JSON Schema

目标架构是"人定义的正轨"，是差距分析器和验证器的输入参照系。

**存储位置**：`<project>/.coderef/target_arch.json`
- 理由：目标架构是"人定义的资产"而非"扫描产物"，应跟随项目进 git 版本控制，可人工编辑，也可由画布导出。
- 与 4.X 的 cache/kg/{md5}.db（扫描产物）区分开。

**Schema 结构**（与讨论稿 5.5 节一致，补充校验规则）：

```json
{
  "version": "5.0",
  "project": "餐厅点餐系统",
  "business_flows": [
    {
      "id": "flow_order",
      "name": "点餐流程",
      "steps": [
        {"id": "s1", "name": "用户进门", "tech_roles": ["waiter"]}
      ]
    }
  ],
  "tech_roles": [
    {
      "id": "waiter",
      "name": "服务员",
      "target_modules": ["waiter.py", "menu.py"],
      "depends_on": ["chef"],
      "depended_by": []
    }
  ],
  "constraints": [
    {"from": "chef", "to": "waiter", "rule": "no_dependency"}
  ]
}
```

**校验规则**（`target_arch_schema.py`，零依赖手写校验）：
- 顶层：version 必填且为字符串；project 可选。
- business_flows：数组，每项含 id（必填唯一）、name、steps（数组）。
- steps：每项含 id（必填唯一）、name、tech_roles（角色 id 数组，须引用已定义角色）。
- tech_roles：数组，每项含 id（必填唯一）、name、target_modules（模块路径数组）。
- constraints：数组，每项含 from/to（须引用已定义角色）、rule（当前仅支持 `no_dependency`）。
- 交叉校验：business_flows 引用的角色 id、constraints 引用的角色 id，必须存在于 tech_roles。

### 3.2 架构差距分析器（arch_gap_analyzer.py）

**输入**：project_path（定位知识图谱）+ 目标架构 JSON
**输出**：结构化差距清单（确定性，不依赖 LLM）

**差距类型与检测方式**：

| 差距类型 | 检测方式 | 严重级 |
|---|---|---|
| `missing`（职责缺失） | 角色声明的 target_modules 在项目中不存在 | high |
| `dependency_violation`（依赖违例） | 模块 A（角色 X）依赖模块 B（角色 Y），且 constraints 禁止 X→Y | high |
| `cycle`（循环依赖） | 复用 arch_audit 的模块级 SCC 检测 | high |
| `business_gap`（业务断链） | 业务步骤关联的所有角色都无有效代码实现 | high |
| `unassigned`（游离模块） | 代码模块不在任何角色的 target_modules 中 | medium |
| `god_module`（上帝模块） | 复用 arch_audit 扇出/扇入+规模判定 | medium |
| `large_module`（异常规模） | 复用 arch_audit 符号数阈值 | low |

**模块名匹配规则**：
- 知识图谱 mod 节点：file_path 为相对路径（如 `core/code_review.py`），name 为 basename 去扩展名。
- 目标架构 target_modules 支持两种写法：**相对路径**（推荐，精确）或 **basename**（宽松匹配）。
- 匹配顺序：先精确匹配相对路径，再 fallback basename 匹配。

**与 arch_audit 的关系**：
- `arch_gap_analyzer` 调用 `arch_audit.audit()` 获取现状症状（cycle/god_module/large_module），不重写。
- 差距分析器额外叠加"现状 vs 目标"对比产生的差距（missing/dependency_violation/business_gap/unassigned）。
- 职责划分：arch_audit 管"现状健康"，arch_gap 管"现状 vs 目标对齐"。

**输出格式**：

```json
{
  "gaps": [
    {
      "type": "missing",
      "severity": "high",
      "role_id": "cleaner",
      "role_name": "保洁",
      "module": "cleaner.py",
      "detail": "目标角色 '保洁' 声明的模块 cleaner.py 在项目中不存在"
    }
  ],
  "summary": {"total": 5, "high": 2, "medium": 2, "low": 1},
  "alignment": {"role_coverage": 0.8, "module_assigned": 0.6, "note": "Phase 0 简化对齐度"}
}
```

### 3.3 MCP 工具设计

| 工具 | 功能 | 后台 |
|---|---|---|
| `coderef_target_arch_set` | 设置/更新目标架构 JSON（校验后落盘） | 否（轻量） |
| `coderef_target_arch_get` | 获取当前目标架构 | 否（轻量） |
| `coderef_arch_gap` | 差距分析（现状 vs 目标） | 否（轻量，纯静态） |

- 三个工具都走 `_handlers` 分发，不加入 HEAVY_TOOLS（纯静态、确定性、速度快）。
- 参数校验复用 `_validate_project_path`。
- 目标架构 JSON 通过参数 `target_arch` 传入（JSON 字符串或对象），`coderef_target_arch_set` 校验后写入 `<project>/.coderef/target_arch.json`。

## 三.5、Phase 1 详细设计：可视化架构画布

### 3.5.1 目标

把"人定义正轨"从 JSON 编辑提升为**可视化拖拽**。画布是 5.0 的产品形态核心。

### 3.5.2 技术选型

- **纯 HTML/CSS/JS + SVG 自包含**（零外部依赖，离线可用），参考 health_dashboard 模式而非 workflow_graph（后者依赖 CDN 的 vis-network）。
- 拖拽：原生 HTML5 Drag & Drop API；拉线：SVG 连线。
- 数据注入：Python 端把知识图谱 + 目标架构 + 差距分析结果序列化为 JSON 内嵌。

### 3.5.3 三层布局

```
┌──────────────────────────────────────────────┐
│ 业务层：业务流程步骤（用户定义，可拉线到角色）    │
│   [点餐流程] → [用户进门] [点菜] [结账]         │
├──────────────────────────────────────────────┤
│ 技术层：技术角色容器（可接收代码模块拖入）        │
│   [服务员: waiter.py menu.py] [厨师: chef.py]  │
├──────────────────────────────────────────────┤
│ 代码层：代码模块节点（自动扫描，可拖拽到角色）    │
│   [waiter.py] [chef.py] [utils.py] [main.py]  │
└──────────────────────────────────────────────┘
```

### 3.5.4 交互与数据流

| 交互 | 行为 | 数据影响 |
|---|---|---|
| 代码模块拖入技术角色 | 定义目标归属 | 更新 `tech_roles[].target_modules` |
| 业务步骤拉线到技术角色 | 定义业务→技术映射 | 更新 `steps[].tech_roles` |
| 差距高亮 | 游离模块灰底 / 依赖违例红连线 / 缺失角色红虚线 / 循环依赖黄框 | 来自差距分析 |
| 导出 JSON | 前端生成目标架构 JSON 并下载/复制 | 用户再经 `coderef_target_arch_set` 落盘 |
| 健康度仪表盘 | 顶部展示差距统计 + 对齐度 | 来自差距分析 summary |

### 3.5.5 MCP 工具

`coderef_arch_canvas`：生成自包含 HTML 画布文件。
- 参数：`project_path`（必填）、`output_dir`（可选，默认 `<project>/.coderef/`）、`target_arch`（可选，缺省读已存储）。
- 返回：HTML 文件路径。
- 纯静态、确定性、轻量同步，不加入 HEAVY_TOOLS。

### 3.5.6 与 Phase 0 的关系

画布是差距分析器的**可视化前端**：数据层完全复用 `arch_gap_analyzer` + 知识图谱，画布只负责渲染与交互。导出 JSON 与 `coderef_target_arch_set` 闭环，形成"画布编辑 → 落盘 → 差距分析 → 画布高亮"循环。

## 三.6、Phase 2 详细设计：重构任务卡 + 对齐验证闭环

### 3.6.1 目标

把差距清单转化为**编程 AI 可执行的重构任务卡**，并在重构后**确定性验证对齐**。这是"AI 执行重构"的落地环节。

### 3.6.2 重构任务卡生成器（refactor_task_generator.py）

**输入**：差距清单（arch_gap_analyzer 输出）+ 目标架构
**输出**：按优先级排序的任务卡列表

每张任务卡字段：

```json
{
  "id": "T001",
  "type": "move_module",          // 任务类型
  "priority": "high",             // 高/中/低
  "title": "将 waiter.py 移入 服务员 角色",
  "gap_ref": "unassigned:waiter.py",  // 关联的差距
  "operations": [                 // 编程 AI 可执行的具体操作
    {"action": "assign", "file": "waiter.py", "target_role": "waiter"}
  ],
  "impact": {                     // 影响范围（图谱确定性查询）
    "callers": ["main.py", "menu.py"],
    "callees": ["utils.py"],
    "files": 3
  },
  "verify": {                     // 验证标准
    "arch": "重构后 coderef_arch_gap 中该差距消失",
    "functional": "coderef_flow_verify 覆盖的流程不退化"
  },
  "dependencies": []              // 依赖的前置任务卡
}
```

**任务类型映射**（差距 → 任务卡）：

| 差距类型 | 任务卡类型 | 典型操作 |
|---|---|---|
| missing | `create_module` | 新建缺失模块 / 补充实现 |
| dependency_violation | `fix_dependency` | 移除违例依赖 / 调整归属 |
| cycle | `break_cycle` | 拆环（提取公共层 / 依赖倒置） |
| business_gap | `implement_flow` | 实现业务步骤对应的代码 |
| unassigned | `move_module` | 将模块移入目标角色目录 |
| god_module | `split_module` | 按职责拆分上帝模块 |
| large_module | `split_module` | 拆分异常规模模块 |

**任务排序**：按任务类型执行顺序（拆环 → 修依赖 → 建缺失 → 实现流程 → 移动归属 → 拆分），其内按严重级（high→low）。依赖拓扑（`dependencies`）当前为占位，见 6.2 遗留疑点。

### 3.6.3 架构对齐验证器（arch_alignment_verifier.py）

**输入**：project_path + 目标架构 + 可选"本次改动文件集合"
**输出**：对齐度评分 + 差距复检

**对齐度评分（0–100，四维）**：

| 维度 | 权重 | 计算方式 |
|---|---|---|
| 职责对齐 | 40% | 已归属模块数 / 总模块数（游离模块惩罚） |
| 依赖健康 | 30% | 1 - 违例依赖边 / 总模块依赖边 |
| 业务覆盖 | 20% | 有实现角色数 / 总角色数 |
| 代码健康 | 10% | 复用 arch_audit 健康度归一化 |

**增量验证**：传入"本次改动文件集合"时，只对受影响子图（改动文件 + 其调用者/被调用者闭包）做差距复检，快速反馈单张任务卡是否达标。不传则全量验证。

### 3.6.4 MCP 工具

| 工具 | 功能 | 后台 |
|---|---|---|
| `coderef_refactor_plan` | 生成重构任务卡列表（差距 → 任务卡 + 影响范围 + 验证标准） | 否（纯静态） |
| `coderef_arch_verify` | 架构对齐验证（四维评分 + 差距复检，支持增量） | 否（纯静态） |

### 3.6.5 闭环

```
画布编辑 → target_arch_set 落盘 → arch_gap 差距 → refactor_plan 任务卡
    → 编程 AI 执行重构 → arch_verify 验证对齐 → 画布高亮更新
```

## 四、设计疑点与决策（自讨论）

### 疑点 1：目标架构 JSON 存哪里？

- 选项 A：独立文件 `<project>/.coderef/target_arch.json`
- 选项 B：知识图谱 SQLite 的 meta 表
- 选项 C：cache 目录（与图谱同级）

**决策：A。** 目标架构是"人定义的资产"，应跟随项目进 git、可人工编辑、可被画布导出复用。存 cache 会随项目路径 hash 漂移且不进版本控制；存图谱 meta 表不便于人工查看和编辑。

### 疑点 2：现状归属（current_role）从哪来？

讨论稿的"职责越界 = 当前归属 ≠ 目标归属"依赖"当前归属"的定义，但 Phase 0 没有画布，无法让用户拖拽定义现状归属。

**决策：Phase 0 简化，不做符号级职责越界检测。** 用"游离模块（unassigned）"表达归属问题——不在任何 target_modules 中的模块即视为未归属，需要人工决定归属。真正的符号级职责越界（如 waiter.py 里有 cook()）依赖 LLM 语义判断，违背确定性优先原则，留给 Phase 1 画布 + 后续版本。

### 疑点 3：依赖违例的约束表达

讨论稿同时给了 `constraints`（no_dependency）和 tech_roles 的 `depends_on`/`depended_by`，语义可能冲突。

**决策：以 `constraints` 为唯一违例判定依据。** `depends_on`/`depended_by` 仅作文档性展示，不参与违例判定。这样语义单一：constraints 声明"禁止的依赖方向"，违反即报 dependency_violation。

### 疑点 4：模块名匹配规则

目标架构里 target_modules 写相对路径还是 basename？

**决策：两种都支持。** 相对路径精确匹配优先（避免不同目录同名文件混淆，与 arch_audit 的 module_of 语义一致），basename 宽松匹配兜底。用户定义时更灵活，误配风险低。

### 疑点 5：差距分析器与 arch_audit 的关系

**决策：复用不重写。** arch_audit 已实现 cycle/god_module/large_module 的成熟检测，差距分析器直接调用 `arch_audit.audit()` 获取现状症状，只新增"现状 vs 目标"对比逻辑。避免两套循环依赖/上帝模块检测逻辑漂移。

### 疑点 6：业务断链如何检测

**决策：业务断链 = 业务步骤关联的所有角色都无有效代码实现。** 有效实现 = 角色的 target_modules 中至少有一个文件真实存在。若步骤关联的角色全部无实现，则该业务步骤在代码中找不到对应实现，报 business_gap。

### 疑点 7：MCP 工具是否需要后台化

**决策：不需要。** 三个工具都是纯静态、确定性、轻量操作（读图谱 + 对比），速度应在秒级。加入 HEAVY_TOOLS 反而增加外层 AI 轮询负担。与 coderef_arch_audit（同步轻量）保持一致。

### 疑点 8：游离模块是否全部报出

大项目未归属模块可能成百上千，全部报出会淹没关键差距。

**决策：游离模块默认只报 top N（默认 50），并在 summary 中给出总数。** 用户可通过参数调整。避免"游离模块"刷屏掩盖 high 级差距。

## 五、验证方案

### 5.1 单元验证

- 用 Coderef-Ai-master 自身作为测试对象（自举）：
  1. 定义一份目标架构（tech_roles 覆盖 core/ 主要模块）
  2. 调用 `coderef_target_arch_set` 设置
  3. 调用 `coderef_arch_gap` 获取差距清单
  4. 人工核对差距类型与严重级是否符合预期

### 5.2 反例验证

- 故意定义一个"错误"的目标架构（如把 core/ 的模块归到错误角色、声明不存在的模块、添加违反实际依赖的约束），验证差距分析器能准确报出。

### 5.3 成功指标（对齐讨论稿 12.1）

- 差距分析器能准确识别 ≥90% 的人工预定义差距
- 差距分析全程确定性、可复现、可追溯到代码证据
