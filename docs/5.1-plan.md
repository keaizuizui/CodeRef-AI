## 一、定位升级：从"一次性重构"到"定期体检"

### 1.1 5.0 核心闭环的成果（已完成）

5.0 已经打通"人定义正轨 → AI 对比差距 → 生成任务卡 → 编程 AI 执行 → 确定性验证"的核心闭环：
- `target_arch`（人工确认的架构管线/正轨）→ `arch_gap`（差距分析）→ `refactor_plan`（任务卡）→ `arch_verify`（对齐验证）→ `arch_canvas`（可视化画布）

但这条闭环是**"单次扫描 → 一次性治理"**模型：跑一次差距、修一批、结束。它缺的是——

### 1.2 5.1 要补的东西：**治理的运营化**

用户的真实诉求（原话）是**"并不是从0开始，而是定期体检"**——让已经难以精准实用的项目，**持续**地保持在人工确认的管线逻辑与系统架构上。这意味着 CodeRef 要从"诊断工具"进化为**"架构治理运营系统"**：

```
┌────────────────────────────────────────────────────────┐
│  定期体检 Cycle                                          │
│  ┌─────────┐   ┌────────┐   ┌──────┐   ┌─────────┐      │
│  │ 建档    │ → │ 差距入库 │ → │ 分流  │ → │ 修复/豁免 │      │
│  └─────────┘   └────────┘   └──────┘   └─────────┘      │
│     ↓              ↓            ↓            ↓          │
│  周期设定        gap=工作项    状态/优先级    复验/归档     │
│                                                          │
│  ┌────────────── 每期体检报告 + 跨期趋势 ──────────────┐   │
│  │  完成率 / 复发率 / 未关闭风险 / 各模块健康走势          │   │
│  └─────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────┘
```

### 1.3 借鉴 plane 的映射表

plane 是成熟的**项目管理执行系统**，其精髓是"把事项变成可追踪、可回顾、可自动化的执行对象"。CodeRef 复用其**概念模型**（不复制其多用户/协作/前端工程），映射到架构治理：

| plane 概念 | CodeRef 5.1 对应 | 说明 |
|---|---|---|
| Workspace | （可选，单机工具多为单仓，暂弱化为顶层 scope） | 需要多代码库集中治理时再引入 |
| Project | 单个代码库/项目 | 治理边界 |
| **Cycle（迭代/冲刺）** | **体检周期 HealthCycle** | 核心：周期性建档→扫描→治理→收尾 |
| **Issue / Work Item** | **治理工作项 GovernanceIssue** | 一个 gap/风险/改进建议 = 一条工作项 |
| **Workflow State 状态机** | **Detected → Confirmed → Fixing → Verified → Archived / Rejected** | 每条工作项带状态 + 活动日志 |
| Module | 治理模块 / 架构组件分类 | 按 tech_role 或架构层归组治理项 |
| Label | 治理维度标签 | 架构违例/依赖/可维护性/性能/安全… |
| Priority / Due / Assignee | 优先级 / 截止 / 负责人（字段可选） | 帮助排定治理节奏 |
| **View（预置视图）** | 预置查询视图 | "严重风险/待处理/本月新增/已豁免…" |
| **Dashboard / Analytics** | **体检报告 + 跨期趋势** | 完成率/复发率/风险分布/健康走势 |
| Comments + Activity Log | 活动日志（审计轨迹） | 每次状态流转、验证、豁免都留痕 |
| Automation | （SPM 生成治理计划后交给编程 AI，复用 5.0 refactor_plan） | 不重复造自动修复，仍"执行交给 AI" |

### 1.4 与 5.0 的关系

- **复用不重写**：差距分析（`arch_gap_analyzer`）、任务卡（`refactor_task_generator`）、对齐验证（`arch_alignment_verifier`）、画布（`canvas_generator`）、图谱（`code_knowledge_graph`）全部直接调用。
- **新增的是"治理壳"**：一个轻量持久化治理库 + 周期管理 + 工作项状态机 + 预置视图 + 报告/趋势。5.0 解决"怎么发现和改正"，5.1 解决"怎么持续管住、不复发"。

## 二、核心技术组件（5.1 交付物）

### 2.1 治理数据库 `core/governance_store.py`

轻量 SQLite，承载所有治理运营状态（可随项目进 git 或仅本地，见疑点 1）。

**核心表**：
- `health_cycle`：体检周期。字段：id、name、description、start_date、end_date、status（open/closed）、note。
- `gov_issue`：治理工作项。字段：id、cycle_id（可空=常驻治理队列）、gap_ref（关联的差距描述）、title、role_id、module、gap_type、severity、status、priority、assignee、due_date、evidence、editable_snapshot（生成时的差距快照）。
- `issue_event`：活动日志。字段：issue_id、at、action、actor、detail。
- `gov_setting`：设置/视图定义（可选）。

### 2.2 周期管理 `core/healthcycle.py`

- `start_cycle`：为某个项目建档一个体检周期；把当前 `arch_gap` 的差距**全量导入**为治理工作项（状态 Detected）。
- `close_cycle`：收尾；统计该期完成率/剩余项/新增/复测通过情况，产出本期报告基础数据。
- `import_gaps`：把某次扫描成果作为"新发现"**并入**当前/常驻治理队列，已存在（同证据+同定位）的工作项自动去重，检测**复发**（曾被切到 Archived 又出现）。

### 2.3 状态机与分流 `core/gov_issue.py`（可并入 store）

- 状态机：`Detected → Confirmed → Fixing → Verified → Archived`；另允许 `Rejected`（人工豁免/确认无需改）。
- `transition`：合法流转 + 校验（如只可从 Confirmed 进 Fixing；Archived 前须 Verified）。
- 每次流转写 `issue_event`，形成审计轨迹。
- 豁免：`reject_issue(gap_ref, reason)` → Rejected，后续扫描同类差距自动并入时不重复报（除非再次扫描确认仍存在并重开）。

### 2.4 预置视图 `core/gov_view.py`

- 提供类 plane View 的预置查询：all、open、by_severity、by_role、recent、rejected、overdue、verified_recently、my_assigned。
- 返回结构化列表，供 MCP 或报告呈现。

### 2.5 体检报告与趋势 `core/gov_dashboard.py`

- 单期报告：完成率、未关闭项、按严重级/模块分布、打断点（blocked）。
- **跨期趋势**：连续各 HealthCycle 的"剩余风险数/完成率/复发数"折线数据，输出给（可选）HTML 报告或 JSON。
- 报告形态：默认 JSON；可选自包含 HTML（复用 health_dashboard / canvas 的渲染模式）。

### 2.6 MCP 工具（新增/扩展）

| 工具 | 功能 | 后台 |
|---|---|---|
| `coderef_gov_start` | 建档体检周期并导入差距为工作项 | 否（纯静态） |
| `coderef_gov_issues` | 查治理工作项（预置视图/过滤） | 否 |
| `coderef_gov_transition` | 工作项状态流转 / 豁免 | 否 |
| `coderef_gov_report` | 体检报告（单期 + 跨期趋势） | 否 |
| `coderef_gov_close` | 收尾体检周期 | 否 |

复用已有：`coderef_arch_gap`（差距来源）、`coderef_refactor_plan`（把 Confirmed 项转任务卡）、`coderef_arch_verify`（复验达标）、`coderef_arch_canvas`（可视化）。

## 三、设计疑点与决策（自讨论）

### 疑点 1：治理数据存哪里？

- 选项 A：`.coderef/governance.db`（SQLite，随项目进 git）
- 选项 B：`cache/kg/`（与知识图谱同目录，不进 git）
- 选项 C：纯 JSON 文件

**决策：A，SQLite 于 `<project>/.coderef/governance.db`，且建议进 git。** 理由：治理状态（已确认/已豁免/负责人/状态/活动）是**人/团队的决策资产**，应持久化、可随项目版本控制、可协作（多人克隆同一仓库共享治理状态）。差距本身可重生成，但"人的注释决策"不应丢。与 5.0 的 `target_arch.json`（同放 `.coderef/`，也随 git）一致。

### 疑点 2："定期体检"的周期如何定？

**决策：周期由人按需创建，不硬性定时。** CodeRef 提供 `coderef_gov_start`（带 name/账号 start/end，默认开始=今天），由使用者/外部调度（如 CI 或 cron）决定多久体检一次。工具本身不做后台定时（MCP 无常驻定时能力），可提示"周期结束未复检离开期"。这样贴合"体检"又保留灵活性。

### 疑点 3：差距如何成为工作项而不重复？

**决策：以"定位键"去重。** 每条差距用 `(gap_type, role_id/module, 定位路径)` 组合成 key；导入时按 key 合并：已存在→更新/标记"仍存在"；曾 Archived 又出现→标记 **recurred**（复发，用于趋势告警）；Rejected 且证据未变→跳过（豁免生效）。

### 疑点 4：豁免（Rejected）会不会掩盖真实问题？

**决策：豁免必留 reason 且可撤销。** Rejected 写入 `reason` + 活动日志；报告单独展示"已豁免"分类，不让其消失；后续扫描若差距**变化**（证据改变/消失），允许自动重新激活并提示复核。防止把治理做成一键忽略。

### 疑点 5：是否引入多用户/权限/协作？

**决策：暂不引入（本次范围聚焦单机/单仓工具形态）。** plane 的 Workspace/权限/实时协作价值在团队 SaaS 场景；CodeRef 目前是 MCP + HTML 报告形态，引入多租户会显著增加复杂度且偏离"体检工具"定位。`assignee` 作为字段先支持（记录负责人名），不做登录/权限。**这与用户"参考实现做项目管理"不冲突**——我们借鉴的是项目管理的**运营模型**（周期/状态/视图/趋势），不是多租户工程。

### 疑点 6：报告用什么形态？

**决策：默认 JSON（MCP 消费），可选自包含 HTML（人看）。** 复用 `health_dashboard.py` / `canvas_generator.py` 的自包含离线渲染模式，报告 HTML 含趋势图（内联 SVG，零 CDN）。跨期趋势由 SQLite 聚合各 HealthCycle，不依赖 LLM。

### 疑点 7：治理库会不会和知识图谱重复？

**决策：职责分离，不混。** 知识图谱（`cache/kg/`）是**扫描产物**（现状），治理库（`.coderef/governance.db`）是**决策状态**（目标+治理运营）。图谱每次扫描重建，治理库持续累积。差距是一次扫描时从图谱得出的"现状 vs 目标"，导入治理库时**留存快照**（editable_snapshot），避免治理记录随图谱重建而漂移。

### 疑点 8：自动化线到哪一层？

**决策：治理自动化只做到"建档+去重+复验+状态机+报告"，不自动修复。** 与 5.0 一致："执行交给编程 AI"。`coderef_gov_transition` 将 Confirmed 项交给 `coderef_refactor_plan` 生成任务卡，修复后 `coderef_arch_verify` 复验，通过 → Verified → Archived。自动化的价值在日常运营，不是写代码。

## 五、验证方案（关键成功指标）

- **去重/复发**：重复建档同一差距，工作项不重复；把已 Archived 的差距重新制造，趋势报出"复发"。
- **状态机**：非法流转被拒；Verified 前不可 Archived；Rejected 留 reason。
- **豁免**：Rejected 分类可见；差距变化后自动重新激活提示复核。
- **趋势**：连续 3 个模拟 Cycle，完成率/复发率/剩余风险曲线正确。
- **闭环**：用 requests 项目跑 `gov_start → gap 入库 → transition → refactor_plan → verify → archived → gov_report` 全链路。
