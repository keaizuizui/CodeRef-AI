## 一、诉求回顾（来自  归档，差距 1/2/3）

1. **差距 1 · 业务层仅 4 步线性主干**：working 调研工具真实流程是 8 阶段（需求澄清→多轮搜索→素材处理→深度抓取→覆盖度评估与补搜→TTD-DR 逐章扩写→Editor 统稿终审→交付物编译），而当前 `bf_research` 只有 4 个线性 step，且其中 `队列分发`/`信源回收入库` 是目标架构自造、真实流程不存在的环节——粒度与顺序都失真。
2. **差距 2 · 阶段内"子模块/适配器矩阵"无处安放**：8 阶段每个阶段内含子模块/适配器矩阵（如阶段 2 的 BochaAdapter/DDGAdapter/XNGAdapter/ZhihuAdapter→mind_search/gptr_service、阶段 6 的 engine.py/TDDRSearchBridge/SearchEngineV2）。`steps` 仅有 `{id,name}`，无嵌套子项、无模块归属插槽；实测 5 个搜索 Adapter 在 target 归一后的可视图命中 0。
3. **差距 3 · 分支回环/决策点画不出来**："素材不足→自动补搜""评分<70→smart 复写""L2/L3 按需补搜""覆盖度阈值按任务类型动态" 全为条件触发与回环，当前画布建模为串行主干，这些"让架构活起来"的逻辑全部丢失。

核心判词（归档 §5）：**不是"符号不存在"，而是"业务层的建模/可视化粒度太粗"**。`business_flows.steps` 裸 `{id,name}` 是表达力瓶颈的第一性约束。

## 二、现状实证（开发方读码确认）

| 层 | 现状 | 代码位置 |
|---|---|---|
| 数据 schema | `step` 必填 `{id,name}`，可选 `tech_roles`；无嵌套子项/无分支回环字段 | `core/target_arch_schema.py` `REQUIRED_STEP_KEYS=(id,name)` |
| 画布渲染（业务层） | 每个 `step` 平铺为一个 `step:{flow}:{sid}` 节点（📈 业务层），经 `tech_roles` 建 `step→role` mapping 边 | `core/canvas_generator.py` L120-132 / L167-176 |
| 技术层 | 每个 `role` 一个节点（🏷），`role→module` belong 边 | L134-149 / L178-186 |
| 代码层 | 每个 module 节点，module→module dep 边 | L152-163 / L188+ |

**关键事实**：working 5 个搜索 Adapter 之所以"可视图命中 0"，不是因为探测不到（ §3.2 证实它们未出现在 target 归一后视图）——而是 `step` 结构没有挂载它们的槽位，且这些类不被任何 `tech_roles.target_modules` 收录，导致 business/tech 两层都没有成员关系把它们拉进视图。所以表现力扩容的关键是给 `step` 增加**阶段→子模块/适配器 的成员挂载**，让画布能沿"阶段 → 成员"把代码层已存在的节点聚合到正确阶段。

## 四、候选方案对比（供取舍）

| 维度 | **方案 A · steps 结构化扩展** | 方案 B · 独立 stages 结构 | 方案 C · 最轻量（仅子项挂载） |
|---|---|---|---|
| 做法 | 保持 step 平铺数组，给 step 追加可选字段 `sub_module_refs` + `branches` + `kind` | target_arch 新增顶层 `business_stages`，`steps` 通过 `stage_id` 引用，阶段可跨流复用 | 只给 step 加 `sub_module_refs`，分支回环降级为节点内文本标注 |
| 阶段子项挂载 | ✅ step 自带子项 | ✅ stages 自带子项 | ✅ step 自带子项 |
| 决策分支/回环边 | ✅ `branches`（条件 step→step 边） | ✅ 最强（边/条件独立建模） | ❌ 仅文本，无法成边 |
| 阶段跨流复用 | 需重复写子项 | ✅ 天然复用 | 无 |
| 向后兼容（旧 target_arch） | ✅ 新字段可选，`REQUIRED_STEP_KEYS` 不变 | ⚠️ 新顶层键，需兜底处理无 stages 的旧流 | ✅ |
| 改动面 | 中（schema + canvas 渲染 + 校验 + business_gap） | 大（新结构贯通 schema/canvas/gap） | 小（schema + canvas 渲染） |
| working 8 阶段自证满足度 | 高（阶段子项 + 条件回环全覆盖） | 高 | 中（分支回环弱化） |
| 过度工程风险 | 低 | 高（跨流复用暂无人要求） | 最低 |

**推荐：方案 A**。理由：
- working 自证需要"阶段子项矩阵 + 分支回环边"两者都表达，方案 C 做不到成边，方案 B 的"跨流复用极简复用"working 当前无此需求，属过度设计；
- 方案 A 改动集中在 `step` 局部字段 + 画布增量渲染，`REQUIRED_STEP_KEYS` 保持 `{id,name}` 不动，旧 target_arch 完全兼容，风险面最小；
- 分支回环用 `branches`（step→step 条件边）建模，足够覆盖归档点名的"补搜/复写/阈值动态"三类回环。

> 若你（用户）判断"阶段很可能跨多条业务流复用、且结构要求严"，再升级到方案 B；若你偏好最快落地、暂可接受分支回环弱化为文本，可用方案 C。当前推荐 A。

## 五、方案 A 详细设计

### 5.1 `steps` 扩展字段（全部可选，向后兼容）

```jsonc
{
  "id": "s3",                // 必填（不变）
  "name": "多轮搜索（搜索矩阵）", // 必填（不变）
  "kind": "phase",           // 可选："phase"＝阶段节点；缺省视为普通 step（旧语义）
  "tech_roles": ["searcher"],// 已有可选：该阶段引用的技术角色

  // —— 新增：子模块/适配器成员挂载（差距 2 的解法）——
  "sub_module_refs": [
    { "module": "adapters/bocha_adapter", "role": "searcher",
      "alias": "BochaAdapter", "kind": "adapter", "note": "商业库搜索" },
    { "module": "services/gptr_service",        "kind": "module" }
  ],

  // —— 新增：分支/回环边（差距 3 的解法）——
  "branches": [
    { "to": "s5", "type": "loop",   "condition": "素材不足 → 触发补搜" },
    { "to": "s6", "type": "loop",   "condition": "评分 <70 → smart 模型复写" },
    { "to": "s2", "type": "fallback","condition": "L2/L3 按需补搜" }
  ]
}
```

要点：
- `sub_module_refs[].module` 用**模块相对路径**（与 `tech_roles.target_modules` 同一匹配语义，可被 `_match_module_ids`/索引精确命中），`alias` 用于显示适配器类名（如 BochaAdapter），`kind: adapter|module` 决定图标归类。
- `branches[]` 的 `to` 指向同 flow 内另一 `step.id`（可为自身之前的阶段，实现回环），`type: loop|if|fallback` + `condition` 描述触发逻辑。
- **不改必填键**：旧 target_arch 无 `kind/sub_module_refs/branches` 时，画布行为与现状完全一致 → 满足"回归不劣化"。

### 5.2 画布渲染增量（`core/canvas_generator.py`）

业务层：
- 保留 step 平铺节点的同时，`kind=="phase"` 的 step 渲染为"阶段分组"风格（放大图标 / 加阶段序号徽章），与普通 step 视觉区分。
- `sub_module_refs` 绘制**阶段→成员** membership 边：to 既有 `role:{rid}`（有 `role` 的成员）或既有 `mod:{module}`（代码层节点）。如此，5 个搜索 Adapter（`mod:adapters/...`）沿其所属阶段被拉进可视图，命中 0 问题自然消解——因为 members 引用的模块必然进代码层节点集合。
- `branches[]` 绘制虚线回环边（from 当前 step → to 目标 step，label=condition），与 mapping 边（绿实）等同属第二类边，可折叠以控噪。

技术层/孤本标注（差距 3 的孤本需求 + ③ 既有数据）：
- 复用 `arch_audit` `identity`/`arch_gap` `twin_identity` 已输出的 fan_in 判定（③ 已实现数据侧），在画布上对命中成员/代码层节点加 `真身/孤本/待收编` 徽章，不新增数据计算，只补渲染。
- `adapters`（BochaAdapter 等）`alias` 命中文档时，作为技术层适配器归类，可归入 `searcher` role 的聚合下（通过 `role` 字段），或独立技术层节点。

### 5.3 `arch_gap_analyzer` / `business_gap` 消费调整

- `_detect_business_gaps` 目前按 `role_has_impl` 判断业务断链；扩展后 `sub_module_refs[].module` 若在项目中无实现，应能提示对应**阶段内成员缺失**，即 stage→member 粒度是否断链（补一个成员级断链检查即可，不重写既有 role 级逻辑）。
- `_match_module_ids` 对 `module` 走既有精确匹配，`alias` 仅展示态不影响判定。

### 5.4 向后兼容 & 校验

- `target_arch_schema` 对三个新字段均"存在才校验"：`sub_module_refs` 为对象数组且 `module` 非空字符串；`branches[].to` 必须能在同 flow 的 steps 中找到对应 id；`kind` 取枚举 `phase|step|""`。旧 target_arch 无这些字段 → 校验零新增错误。

## 六、需要你拍板的决策点

1. **分支回环建模粒度**：方案 A 用 step→step 条件边（`branches`）是否满足？还是必须支持更细的"条件 + 多出口/守卫"（那会更复杂）？→ 建议：step→step 边 + condition 文本，够用且不过度。
2. **适配器孤本标注的呈现层**：5 个 Adapter 是"归入 searcher 角色技术层聚合下"（方案 A 推荐）还是"独立技术层节点"？→ 建议先聚合（避免技术层爆炸），有需要再拆。
3. **membership 只画"阶段→成员"还是也画"成员→模块"链**：方案 A 阶段子项直接引代码层已有模块节点，是否还要沿 role 再走一层？→ 建议阶段→成员直连代码层，保持图不膨胀。
4. **是否先做 working 自证骨架再谈通用**：建议按  期望以 working 调研工具为基准自证 8 阶段，验证通过后再沉淀样板模板（不回写入工具硬编码）。
