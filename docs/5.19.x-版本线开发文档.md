# 1. 背景与问题定义
## 1.1 基线与文档来源
本文档定义 CodeRef-AI v5.19.x 版本线的开发范围与实施方案。基线为 v5.18.13（52 个 MCP 工具、313 项回归全绿），上游输入包括：仓库现状勘察（mcp_server.py、tool_registry、artifact_freshness、pr_whitelist、project_scope、shared_filter 与五份 skill 文档）、v5.18.x 全部 changelog、以及《2026 热点 AI 论文与 CodeRef-AI 引进价值分析报告》（2026-11-09，覆盖 ICLR/ICML/NeurIPS/ICSE/ASE 2026 论文映射与 60 天路线建议）。
v5.18.x 的主题是「让结论可被安全转述」：结果信封（KL-01 至 KL-09 已知限制登记表）、派生产物新鲜度快报、CALLS 作用域收敛、扫描口径统一。这些机制显著提升了结论质量，但一线使用中暴露的问题属于另一个维度——不是结论错了，而是结论被错误地使用。
## 1.2 五大痛点现象
编程 AI 通过编排 skill 作业时，反复出现以下现象（均为一线实测，与信封机制无关，信封只是让问题更容易被观察到）：
表1　五大痛点现象与 5.18.x 机制覆盖度

| 编号 | 现象 | 5.18.x 已有机制 | 覆盖度评估 |
|---|---|---|---|
| P1 | 信息滞后：引用陈旧图谱、旧报告当现状，AI 不主动核对 | artifact_freshness 挂在 coderef_version（可选查询） | 弱——AI 不查 version 就拿不到快报 |
| P2 | 不听从指挥：skill 规定的转场与前置步骤被跳过 | skill 文字纪律 + 信封 blocked_by 提示 | 弱——纪律是文字不是代码，跳过无后果 |
| P3 | 资料存在记忆层又不读取：operation_memory 明明有 recover，AI 不调，重新扫一遍或反问用户 | coderef_operation_memory(action=recover) 是 skill 里标注的首选入口 | 弱——依赖 AI 主动调用 |
| P4 | 图谱落后了也不管：代码已变，coderef_query 仍查旧图且无任何提示 | 新鲜度快报可显示 code_newer，但查询工具自身不带该字段 | 弱——提示不在查询结果里 |
| P5 | 第三方库检索以后需要忽略又不忽略：用户说忽略某库/目录，后续调用仍然扫进来 | pr_whitelist / project_scope / shared_filter 分散实现 | 中——机制存在但入口分散、无持久化、无生效验证 |

## 1.3 根因分析
五个现象指向同一个结构性根因：指挥权错位。当前架构里，编排者（发号施令的）是编程 AI，CodeRef 只是被调用的工具集——所有防护（信封、快报、skill 纪律、白名单）本质都是「建议」，执行与否取决于编程 AI 的自觉。具体拆解为四个缺陷：
缺陷一：纪律以文字存在，不在代码里。skill 的转场规则、先查版本再引用产物的规则，全部是自然语言约定。MCP 协议本身是被动响应模型：工具无法拒绝一个顺序错误的调用，只能在结果里提示。
缺陷二：状态不可见。服务端不知道调用方是否 recover 过记忆、是否刚 sync 过图谱、是否被用户告知过忽略某目录——因为没有会话级状态文件，每次调用都是无状态的，纪律无法被检查。
缺陷三：边界事实源分裂。范围控制散在 project_scope（目录判定）、pr_whitelist（白名单条目）、shared_filter（共享过滤）三处，用户的「忽略」意图没有持久化载体，靠 AI 在后续每次调用中记得传参。
缺陷四：主 AI 上下文过载。52 个工具的描述、用法、注意事项全部压进编程 AI 的上下文，skill 文档 635 行——AI 记不全、记不准，正是「不听指挥」的注意力基础。
由此得出 5.19.x 的中心命题：把纪律从 skill 文字移进服务端代码，把编排权从编程 AI 的自觉移进一个 CodeRef 自己控制的调度层——包括但不限于引入独立子 agent 调度器。
## 1.4 与论文引进价值报告的衔接
价值分析报告识别的六项能力缺口与本版直接相关：MCP 自检（对应第 7 章观测层）、多轮探针（对应 5.19.5 的违规注入测试）、记忆 AST 锚点（P3 对策的后续方向）、动态依赖图（P4 对策的后续方向）、对抗性鲁棒性（第 7 章测试策略）、记忆自进化闭环（5.19.x 之后的长期方向，本版只做地基：记忆强制注入与使用留痕）。
# 2. 设计目标与不变红线
## 2.1 版本线目标
G1 纪律代码化：五大痛点对应的规则全部从 skill 文字迁移为服务端可执行的检查，违规调用返回 blocked_by 信封而不是带病执行。
G2 状态持久化：建立 .coderef/session_state.json 会话状态文件，记录记忆恢复、图谱同步、忽略规则、产物刷新四类事实，让检查有据可依。
G3 调度收口：提供 coderef-dispatcher 独立子 agent 调度器，编程 AI 从「编排 52 个工具」降级为「调用 4 个调度工具」，中间过程不进主 AI 上下文。
G4 观测闭环：所有防护点的命中与绕过行为落盘为审计日志，为后续 eval 扩展与对抗测试提供数据。
## 2.2 不变红线（继承自项目宪法，5.19.x 不放宽任何一条）
确定性优先：审计、图谱、架构诊断、流程验证、变更守护、OWASP 保持纯静态，dispatcher 的规则引擎部分同样零 LLM。
LLM 只用于人话与语义：dispatcher 的 LLM 意图层（5.19.4）是可选项，未配 Key 时硬阻断并降级为规则模式，绝不编造。
诚实状态：missing / outside / SKIP / stale 是事实不是故障，信封语义在 dispatcher 层原样透传，不吞不美化。
可复现：同一项目同一状态下，dispatcher 产出与手工按 skill 编排产出一致（差异仅在被省略的中间步骤）。
向后兼容：dispatcher 不可用时，52 工具裸暴露模式照常可用（降级路径），既有 MCP 客户端与 skill 无破坏性变更。
# 3. 总体方案：三层防线
5.19.x 按「先服务端单侧可做、再调度器、再观测」的顺序分三层推进。三层互相独立可回滚，任何一层失败不影响已交付层。
表2　三层防线与版本映射

| 层 | 内容 | 解决 | 版本 |
|---|---|---|---|
| 层1 服务端闸门 | 结果级新鲜度硬戳、统一范围层、会话状态、记忆前置注入、precondition 检查 | P1/P3/P4/P5 的服务端部分 + P2 的检查部分 | 5.19.0-5.19.2 |
| 层2 调度器 | coderef-dispatcher 独立子 agent：规则引擎 MVP + 可选 LLM 意图层 | P2 的编排部分，全部痛点的根治 | 5.19.3-5.19.4 |
| 层3 观测 | 审计日志、违规遥测、违规注入测试、eval 扩展 | 防退化的持续保障 | 5.19.5 |

层1 的价值在于不等调度器：编程 AI 就算完全不听指挥，只要它调用了工具，工具自身就会带着新鲜度戳、注入的记忆摘要、生效的忽略规则返回——纪律藏在工具背后。层2 才是根治：把「听不听指挥」这个问题本身消灭掉，因为指挥者换成了 dispatcher。
# 4. 痛点逐项对策
## 4.1 P1 信息滞后：结果级新鲜度硬戳
现状漏洞：新鲜度快报挂在 coderef_version 上，是「AI 应该主动查」的可选动作。实测 AI 经常直接引用 .coderef/ 下的历史产物而不查版本。
对策：把 artifact_freshness 的判定下沉进每个依赖派生产物的工具返回。coderef_audit、coderef_query、coderef_arch_gap、coderef_interpret 等 6 个高频工具的信封新增 freshness 块：artifacts_used（本次结论引用了哪些产物）、code_newer（代码是否已比产物新）、stale_reason、refresh_action。AI 引用结论时，滞后信息就贴在结论上，无法剥离。
自动重跑提示升级为自动重跑调度：code_newer=true 且产物超龄时，工具在返回带警告结果的同时，自动把对应刷新任务（如 kg 增量 sync）排入后台任务队列，返回体附带 task_id——AI 只需一次轮询就拿到刷新后的结果。
验收：对同一陈旧产物，5.18.13 的 coderef_query 返回无提示的旧图结果；5.19.x 返回 freshness.code_newer=true 的警告结果，且第二次查询自动使用新图。
## 4.2 P2 不听从指挥：precondition 闸门代码化
现状漏洞：skill 的 gate（如「引用历史产物前先跑 coderef_version」「L2 主链必须先捋管线再定标」）是文字。MCP 工具无法拒绝顺序错误的调用，AI 跳过步骤无人知晓。
对策：为链式工具建立 precondition 注册表。每个工具声明前置条件（依赖的状态事实 + 检查函数），mcp_server 在 _call 入口统一执行检查；未满足时返回 status=blocked、envelope.blocked_by.owner=consumer、owner_actions 给出补齐动作。AI 拿到的是「这次调用没执行 + 为什么 + 该先做什么」，而不是执行了一个带病结果。
首批闸门：G-A「未恢复记忆即调用依赖记忆的工具」→ 引导 recover；G-B「图谱过期即调用图谱查询」→ 引导 sync（或自动触发）；G-C「L2 定标不存在即调用 verify 类工具」→ 引导 target_arch_set；G-D「产物超龄引用」→ 引导重跑。闸门命中与放行均写入审计日志（层3）。
边界：闸门只拦「证据不足的结论路径」，不拦纯只读探查（coderef_version、task_status 永远放行），避免把工具变成迷宫。
验收：注入违规序列（未 recover 直接 query）的自动化用例，断言返回 blocked 而非旧数据；313 项既有回归全绿（既有调用序列不受影响——闸门条件对合法序列恒真）。
## 4.3 P3 记忆不读取：记忆前置注入
现状漏洞：operation_memory(action=recover) 是 skill 标注的首选入口，但依赖 AI 主动调用。实测 AI 要么重新扫一遍（浪费 token 与时间），要么反问用户（体验差）。
对策一（会话首调注入）：会话状态文件记录 recover 事实。会话内首次调用任一重工具（audit/query/report）时，若尚未 recover，服务端自动执行 recover 并把记忆摘要注入返回体的 context.memory_digest 字段（带 recovered_from、条数、最后更新时间）。AI 不调也得调，结果自动带上。
对策二（digest 而非全集）：注入的是摘要（活跃任务、关键结论、未决事项各若干条），不是全量记忆——控制 token 成本，避免注入本身制造滞后。
对策三（使用留痕）：工具消费 memory_digest 时在审计日志记录 hit/miss，为价值分析报告提出的「记忆自进化闭环」积累数据：哪些记忆被引用、哪些从未被读，作为后续记忆分层与淘汰的依据。
验收：无 recover 调用的会话里，首次 audit 返回体含 memory_digest；摘要 token 上限可配置（默认 800 token）；记忆层为空时 digest 为空数组并注明（诚实状态）。
## 4.4 P4 图谱落后：stale-aware 查询与自动增量同步
现状漏洞：图谱查询走 SQLite 静态库，code_newer 判定只在新鲜度快报里，查询结果自身不带。AI 拿到旧图结果时无从察觉。
对策：coderef_query 系列在执行前自动比对代码最新 mtime 与 kg built_at（复用 artifact_freshness 的判定与统一扫描口径，不新增口径）。超阈值（默认 30 分钟或 mtime 变更文件数超过 N）时：结果信封标 stale=true，同时自动触发后台增量 sync 并返回 task_id；下次查询自动使用新图。阈值与行为写入 config，支持「警告不阻塞」与「阻塞等待刷新」两档。
增量同步强化：现状记忆 sync 已是增量（mtime+size），图谱侧补齐文件级增量：只重建变更文件影响到的实体与关系边（AST 粒度定位，复用 ca_parse 的实体索引），目标把万级文件项目的全量重建从分钟级压到秒级。此为价值分析报告「动态依赖图」方向的过渡实现。
验收：修改代码后立即 query，返回 stale=true + 后台 sync task_id；sync 完成后同 query 返回新图且 stale=false；增量正确性用「全量重建结果与增量结果一致」断言。
## 4.5 P5 忽略失效：统一范围层与生效验证
现状漏洞：范围控制三处分散（project_scope 判目录、pr_whitelist 管条目、shared_filter 做共享过滤），用户「忽略这个第三方库」的意图没有持久化载体，靠 AI 记住并在每次调用传参——正是「需要忽略又不忽略」的直接原因。
对策一（单一事实源）：新增 .coderef/scope.json，作为项目边界的唯一权威配置：exclude_globs（忽略路径模式）、include_overrides（误伤找回）、ignore_libs（第三方库名单）、每条带 added_by、added_at、reason。工具侧新增 coderef_scope(action=add/remove/list/verify)，用户或 AI 说「忽略 X」一次，永久生效（可提交进版本库共享给团队）。
对策二（强制过滤收口）：project_scope、pr_whitelist、shared_filter 的三套过滤逻辑统一收敛为 scope 模块的单入口 apply_scope(files)，所有扫描型工具强制经此过滤。5.18.x 已完成的路径段匹配、根目录层级判定等口径全部保留，只收口不重写。
对策三（生效验证回执）：add 忽略规则后立即返回 verify 回执：将被排除的文件数、按工具的分类计数（audit/graph/sca 各排除多少）、被误伤的可疑项（如与项目代码同名）。AI 把回执转述给用户确认，杜绝「以为忽略了其实没生效」。
对策四（忽略豁免边界）：scope.json 只作用于扫描与检索，不作用于 change_guard 的回归防护范围——用户忽略的是「审计噪音」不是「安全责任」，这条写进 skill 与文档，防止把忽略当成放火工具。
验收：add ignore 后立即 audit，被忽略路径不再出现在 findings；verify 回执数字与实际排除一致；change_guard 仍守护被忽略目录内的既有代码变更。
# 5. 子 agent 调度器 coderef-dispatcher 详细设计
## 5.1 设计动机与角色
层1 的闸门解决「单次调用守纪律」，但没有解决「链路编排靠自觉」：三链（L1 探查 / L2 治理 / L3 资产）的转场逻辑、顺序、上下文传递，目前全部写在 skill 文字里，由编程 AI 执行。dispatcher 把这个执行者换成 CodeRef 自己的进程——编程 AI 只表达意图与目标，不再手工编排工具链。
表3　dispatcher 前后的职责划分

| 关注点 | 现状（编程 AI 编排） | 5.19.x（dispatcher 编排） |
|---|---|---|
| 工具选择 | AI 从 52 个工具 + 635 行 skill 文档中自行判断 | dispatcher 按链定义选择，AI 只见 4 个调度工具 |
| 顺序与 gate | skill 文字纪律，可跳过 | 状态机代码判定，跳过即 blocked |
| 记忆与新鲜度 | 依赖 AI 主动 recover / 查版本 | dispatcher 启动即 recover、产物引用前强制刷新检查 |
| 忽略规则 | AI 每次调用传参 | scope.json 单一事实源，自动应用 |
| 中间结果 | 全部进主 AI 上下文（信息滞后 + token 膨胀） | 上下文隔离：主 AI 只收最终摘要信封 |
| 结论可信度 | 取决于 AI 是否读了信封 | 信封由 dispatcher 汇总透传，KL 编号原样携带 |

## 5.2 架构与三种实现形态
dispatcher 是一个独立运行时（同仓、同进程模型可选），对外仍以 MCP server 形态暴露，对内经既有工具注册表直接调用 52 个工具函数（进程内调用，不走 JSON-RPC 回环）。三种形态按确定性红线排序：
表4　dispatcher 三种实现形态

| 形态 | 构成 | 定位 |
|---|---|---|
| A 规则引擎版 | 状态机 + precondition 注册表 + 链定义 DSL（YAML 声明 L1/L2/L3 步骤、gate、产物） | MVP 与默认形态，零 LLM、确定性可复现，5.19.3 交付 |
| B LLM 意图层 | 在 A 之上加一层：自然语言意图 → 链选择与参数抽取（复用 coderef_eval 的 LLM 通道或 MCP sampling） | 可选增强，5.19.4 交付，无 Key 硬阻断降级回 A |
| C 混合自适应 | A 负责全部执行与闸门，B 只做意图理解；意图置信度低时反问（或 MCP elicitation 询问用户） | 5.19.4 后根据 B 的实测误判率决定是否启用 |

选型结论：A 是产品本体，B/C 是增强件。这样红线不被触碰——即使用户配了 Key，审计结论仍然全部来自规则引擎与静态分析，LLM 只影响「选哪条链」不影响「结论是什么」。
## 5.3 对外契约：四个调度工具
表5　dispatcher 暴露的 MCP 工具

| 工具 | 同步性 | 说明 |
|---|---|---|
| coderef_plan | 同步 | 输入意图（枚举值：probe/governance/asset/single_audit/recover 等）与项目路径；输出计划卡：将执行的链、步骤、预计工具数、预计时长、需要的用户决策点。纯规划不执行 |
| coderef_execute | 异步 | 输入 plan_id（或意图直接执行默认链）；返回 task_id 复用既有后台任务与轮询机制。执行中每步过闸门，违规步骤自动补齐（如自动 recover）而非阻塞终止 |
| coderef_dispatch_status | 同步 | task_id 查询：当前步骤、gate 命中记录、已消费/被省略的工具调用摘要 |
| coderef_dispatch_report | 同步 | 任务完成后的最终摘要信封：结论 + freshness 块 + KL 限制引用 + owner_actions + 中间步骤索引（可追溯但默认折叠） |

关键设计：违规自动补齐。与层1「blocked 退回」不同，dispatcher 场景下调用方是自己的执行器，跳步可以当场补救（缺 recover 就先 recover，图旧就先 sync），主 AI 感知的只是多花了几秒。blocked 语义保留给层1 的裸工具模式。
## 5.4 调度状态机与上下文隔离
链定义以 YAML 声明（治理主链为例）：捋管线 → 架构诊断 → 定标（需用户确认点）→ 治理 → 验证 → 体检。每步声明：工具名、参数模板、前置状态、产物键、失败策略（重试/降级/停链询问）。状态机推进落盘 .coderef/dispatch/<task_id>.json，崩溃可恢复（复用后台任务模型）。
上下文隔离：主 AI 只接收 plan 卡与最终 report 信封，中间 52 个工具的返回不进主 AI 上下文。这是 Claude Code 式子代理模式的核心收益：token 从 O(工具调用总数) 降到 O(任务数)，信息滞后因中间结果不再逐条流经主 AI 而结构性消失。
隔离的例外通道：需要用户决策的点（如定标确认）经 coderef_dispatch_status 主动浮出，或走 MCP elicitation 直接询问用户——决策权始终在用户，dispatcher 不替用户做治理决策。
回放与审计：每个 dispatch 任务存完整执行轨迹（工具调用序列、gate 判定、记忆注入命中），既是审计素材也是 eval 评测的输入（层3）。
## 5.5 与既有三链、五 skill 的关系
不替代 skill：五份 skill（coderef-mcp/probe/governance/governance-semi/asset）保留为「人读的编排文档」与裸工具模式的指引；链定义 YAML 从 skill 文档机械导出（同一事实源维护，避免双头更新）。
转场判定收编：skill 里「先判场景再选链」的入口判定表，在 dispatcher 形态 B 下由 LLM 意图层执行、形态 A 下由 coderef_plan 的枚举意图承接（AI 选意图枚举值，比选链更粗粒度、更难选错）。
governance-semi 的软入口档位（先诊断再决策是否升级主链）在链定义里表达为条件分支节点，判定函数确定性实现。

# 7. 测试与质量保障
## 7.1 测试策略
回归基线：313 项既有回归 + 每版本新增用例，全量绿为发布门槛（项目既有纪律，本版新增预计 40-55 例）。
违规注入测试（新）：模拟「不听指挥的 AI」——脚本化生成跳步、乱序、忽略失效、引用陈旧产物的调用序列，断言层1 闸门全部拦截且信封指引正确。这既是 5.19.5 的交付物，也是每个中间版本的自测手段，对应价值分析报告的多轮探针与对抗性鲁棒性建议。

# 8. 风险与开放问题
表8　风险登记

| 风险 | 分析 | 应对 |
|---|---|---|
| 闸门过严伤体验 | blocked 语义滥用会让 AI 在迷宫里打转 | 闸门只拦结论路径不拦只读探查；blocked 必附 owner_actions；灰度期先 warn 后 block |
| dispatcher 成为单点 | 调度器故障影响全部链 | 降级路径为产品特性而非兜底（5.6）；裸模式永远可用 |
| 链定义与 skill 双头维护 | YAML 与 skill 文档漂移 | YAML 为唯一事实源，skill 文档生成式同步（CI 校验一致性） |
| LLM 意图层误选链 | 形态 B 的选择错误传导到执行 | plan 卡先展示给主 AI 确认再 execute；意图枚举兜底；误选率进 metrics 观测 |
| scope.json 滥用为放火工具 | 用户忽略掉安全相关路径 | change_guard 不受 scope 影响（4.5 对策四）；verify 回执暴露误伤项 |
| token 摘要质量 | memory_digest 摘要差导致新形式的信息滞后 | 摘要模板可配置；hit/miss 数据回流调优；上限默认 800 token |

开放问题一：dispatcher 是否需要支持跨项目并行会话——待首个用户实测后决策（当前模型按单项目单会话设计）。
开放问题二：链定义 DSL 是否开放给用户自定义（治理流程个性化）——5.19.3 先内置只读，开放度待定。
开放问题三：MCP sampling 与 elicitation 的客户端支持率参差（2025-11-25 规范），形态 B/C 的通信通道以自有 Key 通道为保底实现。
